## Context

The dictionary now documents grammar that **does not exist in the engine yet**. The `rule_validation_service.py` validation regex and the parser do not support `!=`, `not >`, `not <`, `not >=`, `not <=` as comparison operators, nor do they validate `virtual ONE`/`virtual ALL` naming conventions. The user has now asked "what are future grammar?" — this likely means they want to understand what new grammar features need to be implemented in the engine.

## Key Engineering Discovery

The dictionary introduces two categories of grammar:

### 1. Grammar that MUST be implemented in the engine (new syntax)
| Feature | Status | Required Changes |
|---------|--------|-----------------|
| `!=` operator | Not in parser/validator | Update `_COMPARISON_PATTERN` in `rule_validation_service.py`; update `ComparisonLine`/`FactValue` comparison logic |
| `not >` / `not <` / `not >=` / `not <=` | Not in parser/validator | Update `_COMPARISON_PATTERN`; implement negated comparison logic |
| `virtual ONE` naming convention | Not validated | The engine auto-generates `VirtualNode-*` names — validation could warn about misnamed virtual nodes but is optional |
| `virtual ALL` naming convention | Not validated | Same as above — convention enforcement, not parser change |

### 2. Grammar that is purely convention/documentation (no engine changes)
| Convention | Notes |
|------------|-------|
| `AND NOT` only for negated rule statements | Already how parser works — `AND NOT` only appears on child rules; the scoping rule is about authoring conventions |
| `virtual ONE` = OR, `virtual ALL` = AND | Engine auto-names virtual nodes `VirtualNode-*` — user-authored naming is purely a documentation convention |
| `= TRUE` / `= FALSE` as anti-pattern | Already flagged in dictionary; these parse but are semantically wrong (treat rules as comparisons) |
| `KNOWN` on non-child lines | Already blocked by parser — KNOWN only valid with AND/OR prefix |

## Decision Needed

**The `!=` and `not >` / `not <` / `not >=` / `not <=` operators were introduced in the dictionary but don't exist in the engine.** These need either:
1. **Option A**: Implement them in the engine (update `rule_validation_service.py`, `_COMPARISON_PATTERN`, and the comparison/evaluation logic in `ComparisonLine`/`InferenceEngine`)
2. **Option B**: Remove them from the dictionary and use `AND NOT <variable> = <value>` / `AND NOT <variable> > <value>` instead (which is already supported)

## Implementation Plan (Pending User Decision on Option A vs B)

### Phase A: Example file cleanup (MRCA Chapters 2-7, VEA Parts II-VIII)
Transformations to apply to each file:
1. `= TRUE` → plain rule statement (remove `= TRUE`)
2. `= FALSE` → depends on Option A/B decision:
   - Option A: `AND NOT <rule>` for rule statements, `!=` for comparisons
   - Option B: `AND NOT <rule>` for rule statements, `AND NOT <var> = <val>` for comparisons
3. String literals like `= "value"` → use `IS IN LIST:` with FIXED list, or `IS` for value declaration
4. AND/OR at same level → restructure with explicit OR groups using `virtual ONE`
5. `ITERATE: LIST OF` → `IN` with proper `COLLECTION` declarations
6. `KNOWN` on non-AND/OR-prefixed lines → add proper AND/OR prefix or restructure
7. Missing FIXED list declarations for `IS IN LIST` references → add them

### Phase B: Engine implementation (if Option A chosen)
1. `src/services/rule_validation_service.py`: Update `_COMPARISON_PATTERN` to accept `!=`, `not >`, `not <`, `not >=`, `not <=`
2. `src/domain/nodes/comparison_line.py`: Add negated comparison operator handling
3. `src/domain/tokens/tokenizer.py`: If needed, update tokenisation for multi-token operators like `not >`
4. `src/domain/inference/inference_engine.py`: Handle negated comparison evaluation
5. Tests: `tests/contracts/` and `tests/` for negated comparison parsing and evaluation
